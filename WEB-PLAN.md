# WEB-PLAN: шахматная платформа на собственном движке

Сайт в духе chess.com на собственном движке (Go, нейросеть NNUE): разбор партий, игра онлайн и с ботами, задачи, дебюты. Здесь: что решено, что работает, что дальше. Читать первым раздел «Текущее состояние».

## 1. Принципы

- Движок свой и работает внутри продукта; сервер видит его только через фасад `engine/engine.go`.
- Ядро сайта: сыграли (с человеком, ботом или движком), нажали «Разбор», получили график, классы ходов, точность, дебют и лучшие продолжения. Всё считает наш движок.
- Стек: бэкенд Go + MySQL 8, фронтенд React (Vite), всё в Docker Compose; вход гостем или через Google.
- Небольшие проверяемые шаги, у каждого функции тесты и проверка в браузере.

## 2. Цель и границы продукта

Рабочее название: **Dyanis Chess** (можно сменить).

Приоритеты по вашему порядку:
1. **Анализ партий** — основа продукта.
2. **Онлайн-игра** двух людей с часами, затем «разобрать партию» одной кнопкой.
3. **Задачи.**
4. **Заучивание дебютов.**
5. **ИИ-тренер** — объяснение ошибок и персональные рекомендации (на базе пп. 1–4).

Критерий успеха: два человека играют партию на сайте, жмут «Разбор» и получают
график оценки, классификацию ходов, точность, названия дебютов и лучшие продолжения.
Все оценки считает ваш движок.

## 3. Архитектура и стек

Главное решение: **бэкенд на Go в том же модуле, что и движок.** Тогда сервер просто
вызывает движок через фасад `engine/engine.go` (позиции, ходы, поиск), без IPC и без
перекодирования правил.

| Слой | Выбор | Почему |
|---|---|---|
| Бэкенд | Go, `net/http` + WebSocket (`nhooyr.io/websocket` или `gorilla`) | Один язык с движком; WS и горутины подходят для партий и часов |
| Движок для анализа | **Нативный на сервере**, пул воркеров, NNUE + SIMD | Намного быстрее wasm (в wasm нет SIMD из `GOEXPERIMENT=simd`, это только amd64); Linux-сборки уже делались |
| Движок в браузере | Остаётся `engine/cmd/wasm` (сейчас **без нейросети**, на ручной оценке, около 2700 против ≈ 2800 с сетью) | Игра с ботом без сервера, демо без бэкенда. Сеть в браузере возможна (загрузка файла сети, ~1,5 МБ), но без SIMD будет заметно медленнее; пока бот в браузере слабее анализатора на сервере, и это нормально |
| База данных | **MySQL 8** (решение автора: MySQL или SQL Server; рекомендую MySQL), драйвер `go-sql-driver/mysql`, миграции `golang-migrate` или `goose` | Бесплатный, лёгкий в Docker (~500 МБ ОЗУ), есть тип JSON для сырых данных разбора. SQL Server тоже работает в Docker (`mcr.microsoft.com/mssql/server`, драйвер `go-mssqldb`), но ему нужно от 2 ГБ ОЗУ, а на небольшом VPS это ощутимо; выбирайте его, только если кафедра требует |
| Фронтенд | **React** (решение автора), уже есть: Vite + `react-chessboard` (MIT) | Не переписывать; `chessground` — GPL, не брать |
| Часы и матчинг | В памяти сервера (одна машина) | Redis не нужен, пока один инстанс |
| Аутентификация | **Вход через Google** (OAuth 2.0 / OpenID Connect, `golang.org/x/oauth2` + `coreos/go-oidc`), сессия в cookie `HttpOnly`; гость создаётся одним запросом | Гостевой вход — главная идея воронки chess.com; почта и пароль не нужны, значит, нет хранения паролей и сброса |
| Деплой | **Docker Compose**: `server` (Go + движок + сеть), `web` (nginx со статикой React и прокси `/api`, `/ws`), `db` (MySQL с томом) | Одна команда `docker compose up`, одинаково на ноутбуке и на VPS |

Что проверить до старта: как сейчас устроен `App.jsx` (кто проверяет легальность ходов
на клиенте: wasm или `chess.js`) и чем занят `engine/cmd/wasm`. От этого зависит, нужен ли
отдельный клиентский валидатор.

Структура репозитория (с 2026-10-15; движок, сервер и интерфейс — три независимые части):
```
engine/                     движок целиком; снаружи виден только фасад engine/engine.go
  internal/                 board, movegen, eval, nnue, search, book, uci, ... (закрыто компилятором)
  cmd/ train/ assets/ ...   инструменты, обучение сети, книги, сеть net-kingf-m4.bin
backend/
  cmd/server                HTTP + WebSocket (статику отдаёт nginx в контейнере web)
  cmd/analyze               разбор партий в терминале
  internal/pgn              разбор/запись PGN (правила — через фасад движка)
  internal/analysis         пакетный разбор партии, классификация, точность
  internal/eco              названия дебютов (ECO, справочник lichess), книжные позиции
  internal/api, store       HTTP API, MySQL и миграции
  internal/auth             гости, вход через Google, сессии в cookie
  internal/play             онлайн-партии: комнаты, правила, часы, WebSocket
web/                        фронтенд (React); src/themes — наборы фигур, доски, фоны, звуки
deploy/                     Dockerfile сервера и web (nginx), docker-compose.yml в корне, .env.example
```
Замена движка: сохранить API `engine/engine.go` (тесты контракта — `go test ./engine/`),
остальное не меняется. Подробности в `engine/README.md`.

## 4. Функции по приоритетам

### 4.1. Анализ партий (ядро)

Вход: PGN (вставка/файл), партия, сыгранная на сайте, позже импорт с chess.com по их
публичному API (`/pub/player/{u}/games/{YYYY}/{MM}`, поле `pgn`).

Как считать:
- **Оценка каждой позиции** пакетом: фиксированное время или глубина (например 200–300 мс
  на позицию, MultiPV 2). Партия в 80 полуходов ≈ 20–30 с на одном потоке, поэтому
  анализ идёт **в очереди воркеров** с прогрессом по WebSocket/SSE.
- **Кэш по FEN** (и параметрам анализа): повторы дебютов не пересчитываются.
- **Вероятность выигрыша** из centipawn: `W = 1/(1+exp(-cp/K))`. Значение K нельзя брать
  от Stockfish/lichess: у вашей NNUE своя шкала. Подобрать K подгонкой по вашим данным
  (в `data/nnue` уже есть позиции с результатами партий) — это отдельная задача.
- **Классификация хода** по потере вероятности выигрыша между «лучшим» и сыгранным ходом.
  Стартовые пороги (подобрать по опыту, не по догме): неточность ≥ 5 %, ошибка ≥ 10 %,
  зевок ≥ 20 %; «лучший», «отличный», «хороший» — ниже. Дебютные ходы из книги помечаются
  отдельно (`backend/internal/eco`, ECO).
- **Особые отметки**: «единственный ход» (MultiPV: второй вариант хуже на ≥ 15 %),
  «блестящий ход» (жертва материала, не ухудшающая оценку) — только если успеете
  и сможете проверить; ложные срабатывания хуже их отсутствия.
- **Точность игрока** (изменено 2026-10-15): по каждому ходу `103.17·exp(−0.055·Δwin%) − 3.17`
  (форма как у lichess, на четверть круче: у chess.com цифры ниже), по партии — среднее из
  **взвешенного по остроте среднего и гармонического среднего**, как в формуле lichess: вес хода —
  стандартное отклонение вероятности выигрыша в скользящем окне позиций (от 0.5 до 12), так что
  ошибка в решающий момент весит больше, чем неточность в тихой позиции. Прежняя версия
  (крутизна 0.08 и чистое гармоническое среднее) сносила точность почти в ноль от одного зевка:
  пользователь это отметил. Теперь один грубый зевок в партии из 30 ходов оставляет точность
  в районе 70–90, то есть снимает долю, а не всё. Сверка по партии из `testdata` (chess.com
  показывает 82 / 92): получается 87 / 96 (по крутизне lichess 89 / 97, по прежней 85 / 96).
  Мат — всегда лучший ход (`givesMate`): даже если движок предпочитал другой мат или видел
  мат быстрее, ход, ставящий мат, получает класс «лучший» и потерю 0. Это модель проекта,
  не копия chess.com. Глубина анализа (12, 16, 20) на результат почти не влияет.
- **Ключевые моменты**: самые большие провалы оценки, где партия перевернулась.

Интерфейс: доска, график оценки по ходам (клик = переход), список ходов с иконками
классификации, линии движка (3 линии, глубина), название дебюта, навигация по ходам,
кнопка «сыграть с этой позиции против бота».

Этот же модуль даёт материал для всех остальных пунктов: ошибки → задачи, дебютные
отклонения → тренер дебютов, статистика ошибок → тренер.

### 4.2. Онлайн-игра

Минимальный «играть вдвоём», сначала без рейтинга и матчинга:
- Создание партии по **ссылке-приглашению** («Play a Friend»), выбор контроля времени,
  цвета. Гостевой вход. Затем «быстрый подбор» по очереди.
- Сервер — единственный источник правды: проверка ходов (`engine/internal/movegen`), часы,
  сдача, предложение ничьей, отмена, конец по времени/мату/пату/повторению/50 ходам.
- События WebSocket: `game.start`, `game.move`, `game.clock`, `game.end`, `draw.offer`,
  `presence`. Переподключение клиента с догрузкой состояния обязательно.
- Конец партии → запись в БД (PGN) → кнопка «Разбор».
- Позже: рейтинг Glicko-2 по форматам, список текущих партий, зрители.

### 4.3. Задачи

- База: открытая база задач Lichess (CC0, миллионы позиций с темами и рейтингом) —
  импортировать подмножество, не всё.
- Решение: ход за ходом, проверка по решению, рейтинг задачи и пользователя (Glicko-2/Elo),
  фильтр по темам, подсказка, «задача дня».
- **Фишка**: задачи из **собственных ошибок** пользователя (позиции, где он зевнул,
  из анализа партий). Режим на время (Puzzle Rush) — позже.

### 4.4. Заучивание дебютов

- Репертуар = дерево линий пользователя (PGN, возможность строить в интерфейсе).
- Тренировка: показывается позиция, пользователь вводит ход репертуара; интервальное
  повторение (Leitner или SM-2) по каждой позиции; отдельно «слабые места».
- Источники: каталог ECO из `backend/internal/eco` (`Book.InBook` и `Lookup` по хешу позиции; `engine/internal/openings` — другое, стартовые позиции для матчей); при отклонении от репертуара движок
  показывает, насколько ход хуже.
- Проверьте лицензии книг (`komodo.bin`, `performance.bin`, `gm2001.bin`), если
  выкладывать их в публичный репозиторий или сайт.

### 4.5. ИИ-тренер (в последнюю очередь)

Честное разделение:
- **Что умеет движок**: оценка, лучший ход, цепочка, потеря оценки, тип ошибки по
  простым признакам (потеряна фигура, пропущен мат, пропущена тактика, пассивный ход).
- **Что не умеет**: объяснять человеческим языком «почему».
Варианты, от простого к сложному:
1. **Шаблонные объяснения** по признакам позиции («вы оставили слона без защиты, ход X
   выигрывал его») — детерминированно, без внешних сервисов.
2. **Языковая модель поверх фактов движка**: модели передаются FEN, сыгранный ход, лучшая
   линия и признаки; она формулирует текст. Шахматы сама не считает. Нужны API-ключ и
   лимиты расходов; решайте до начала.
3. **Персональные рекомендации** из статистики по партиям: в какой фазе больше ошибок,
   какие дебюты недоучены, какие темы задач слабые, какие предложить упражнения.
Рекомендация: п. 1 + п. 3 как основа, п. 2 — как опция.

### Настройки «Игровой процесс» (2026-10-17)

По просьбе автора, пункты списка chess.com. Файлы: `web/src/settings/GameplayPanel.jsx` (страница; `controls.jsx` — общие `Row`, `Switch`, `SaveBar`, `SoonRow`), `model.js` (19 новых настроек, `GAMEPLAY_KEYS`, `defaultsOf(gameplay)`: у каждой страницы свой сброс; числовые поля с границами), `components/boardrules.js` (чистая логика доски с тестами: способ рокировки `resolveMove`/`targetSquares`, превью хода `previewPlacement` для подтверждения, ходы для премува `premoveMoves`/`premoveToPlay`, позиция после очереди премувов `queuedPosition`). Адрес `#settings/play` (меню настроек переключает раздел, `history.replaceState`).

- **Доска** (`components/Board.jsx`): `showLegalMoves`, `alwaysQueen` (Alt, слушатель клавиш, при переносе сбрасывается по `blur`), `castling` (при `rook` король на две клетки не рокирует), `confirmMove` (ход ждёт кнопки; `position` показывает превью, кнопки под доской, Esc отменяет), `premove` (при `disabled` доска даёт выбрать свои фигуры по геометрии хода без учёта шаха, поля красные, `onSet`/`onClear`; пешка до последней горизонтали превращается в ферзя; фигуры скользят сквозь чужие, но не свои).
- **Комната партии** (`online/GameRoom.jsx`): премувы — очередь до 30 ходов (`pre`, `MAX_PREMOVES`); доска (`Board`, `premove.queue`) показывает позицию после всей очереди и выбирает следующий ход на ней, красные поля у всех ходов очереди; эффект играет первый, когда `game.turn === you` и он есть в `game.legal`, остальные ждут своих очередей, невозможный сбрасывает всю очередь, сигнал времени `online/lowtime.js` (звук `lowtime` в `sound.js`), подтверждение сдачи и ничьей (`confirmGiveUp`; сдача без подтверждения одним нажатием), `autoReview` (при окончании партии открывает разбор один раз), `whiteBottom` (ориентация; полосы игроков следуют за ней). Игра против движка (`App.jsx`): те же `whiteBottom` (полосы игроков стали значениями `engBar`/`youBar`) и `confirmGiveUp`.
- **Одна партия за раз:** `ensureNoGameRunning` (`online/api.js`) смотрит `GET /api/games` на статус `playing` в лобби и у ботов; запрет только на стороне клиента.
- **Подбор:** `match.Request.RangeDown/RangeUp` (0 — без границы, до 3000), `within(a, b)` проверяется в обе стороны; тест `TestRatingLimitsOfBothSidesApply`.
- **Задачи:** `GET /api/puzzles/next?level=easier|normal|harder|random` (`levelRating`: ±150 или случайный сдвиг до ±300, границы 400–3000, тесты `TestLevelRating`, `TestNextUsesTheLevel`); `puzzleRating` скрывает рейтинг и прирост, `puzzleThemes` показывает темы до решения, `puzzleTimer` — секундомер в верхней полосе (`PuzzlesPage.jsx`).
- **Разбор:** `showEval` скрывает шкалу, график и число оценки (`ReviewView.jsx`), `moveIcons` — значки в `MoveList.jsx`.
- **Не сделано (на странице бледные строки «скоро»):** заочные партии (подтверждение хода, автозаявка победы, дни на ход, переход к следующей партии), режим отпуска, друзья и вызовы (разрешить вызовы, входящий рейтинг, игнор рейтинга друзей, вызовы оффлайн, уведомления), показ времени хода (в `MoveRec` нет времени), очки за задачи, комментарии и подсказки Тренера. «Показывать отзывы после игры» сделано как автоматический разбор движком, без Тренера. Премув в игре с ботом и онлайн; выбор настроек на сервере хранится в `User.settings`.
- **Проверено в Edge (две сессии):** премув чёрных исполнился после хода белых (ходы «1. e4 e5»), подтверждение хода (кнопки, отмена, подтверждение), белые внизу у обоих, подтверждение ничьей, сдача без вопроса, страница настроек сохраняется и переживает перезагрузку, у страницы «Доска и фигуры» нет строки про центр. Не проверено в браузере: рокировка «король на ладью», «всегда ферзь» с Alt, сигнал времени, таймер задачи (логика покрыта тестами `boardrules`, `lowtime`, `model`).

**Перетаскивание фигур в конструкторе дебютов (2026-10-17, по жалобе автора «драг-н-дроп баганный»):** после первого хода фигуры переставали перетаскиваться (клики работали). Причина: допустимые ходы там приходят с сервера позже новой позиции, а `react-chessboard` хранит правило `isDraggablePiece` от рендера, в котором фигура появилась, и устаревшее замыкание навсегда запрещало тащить. В `Board.jsx` правило теперь стабильная функция, читающая свежие данные из ref. Проверено в Edge (`dragstart` приходит на каждом ходу; три хода подряд в конструкторе). Тот же приём нужен для любого нового обработчика, который передаётся в библиотеку доски.

### Аккаунты: гости и вход через Google (2026-10-15, этап 0, вторая часть)

- **Что есть.** Гость создаётся одним запросом (`POST /api/auth/guest`, имя «Гость 1234»), вход через
  Google (`GET /api/auth/google/login` → согласие Google → `/api/auth/google/callback`), выход, `GET /api/me`.
  Страница «Аккаунт» (кнопка внизу меню: «Войти» или имя), страница «Мои партии» со списком разборов
  (результат, дебют, точность, удаление), настройки доски хранятся на сервере и идут за пользователем
  на другое устройство (при входе побеждает копия сервера; если её ещё нет, загружаются настройки этого
  браузера; изменения уходят через 0,6 с, а при закрытии вкладки сразу).
- **Безопасность.** Сессия: случайный токен в cookie `dyanis_session` (`HttpOnly`, `SameSite=Lax`,
  `Secure` под https), в базе только SHA-256 токена. Токен обновляется при каждом входе, старая сессия
  удаляется. От подделки запросов защищает `SameSite=Lax`, а настройки принимаются только с
  `Content-Type: application/json`. Состояние OAuth (`state`) лежит в отдельной одноразовой cookie на
  10 минут. Пароли и токены Google не хранятся: код обменивается на токен доступа и сразу запрашивается
  профиль (`sub`, имя, почта, фото). Гостей не больше 30 в час с одного адреса. Секрет клиента Google
  читается только из переменной окружения, не из флага (флаги видны в списке процессов и в `-h`).
- **Гость → Google.** Гость, входящий через Google, превращается в Google-пользователя на месте (партии
  и настройки остаются); если этот Google-аккаунт уже известен, партии гостя переносятся к нему, а
  гость удаляется.
- **База** (`0002_users.sql`, `0003_analyses_owner.sql`): `users` (id, kind, `google_sub` UNIQUE, имя, почта,
  фото, `settings` JSON), `sessions` (хеш токена, срок), у `analyses` появились `user_id` (при удалении
  пользователя разбор остаётся анонимным, ссылка живёт) и `summary` (точность, дебют: чтобы список не
  читал отчёты целиком). Просроченные сессии удаляются при запуске сервера.
- **API:** `GET /api/analyses` (мои, новые сверху; идущие разборы тоже, чтобы перезагрузка их не теряла),
  `DELETE /api/analyses/{id}` (только своё, 409 пока разбор идёт). Ссылка на разбор открывается всем.
  Без `-dsn` аккаунтов нет, сайт работает как раньше, а страница «Аккаунт» говорит об этом.
- **Настройка Google.** В Google Cloud Console → «Учётные данные» → OAuth-клиент (тип «Веб-приложение»)
  → «Разрешённые URI перенаправления»: `http://localhost:8080/api/auth/google/callback` (для боевого
  домена свой адрес с https). Ключи в `.env`: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `PUBLIC_URL`.
  Пока приложение на экране согласия в статусе «Тестирование», входить могут только добавленные в
  «Тестовых пользователей» адреса.
- **Тесты:** `internal/auth` с подменой базы и подставным Google (новый пользователь, повторный вход,
  превращение гостя, слияние, поддельный и повторный `state`, отказ пользователя, отказ Google, лимит
  гостей, поддельная cookie, настройки), `internal/api` (владельцы, список, удаление), `internal/store` на
  настоящей MySQL (пользователи, сессии, срок, слияние, `ON DELETE SET NULL`). Вручную в Edge: гость,
  разбор, «Мои партии», удаление, выход, перенос настроек на «чистый» браузер.
- **Не сделано:** сам вход через Google не проверен до конца: Google ответил `redirect_uri_mismatch`
  (адрес возврата ещё не внесён в консоль). Уборка гостей, которые давно не заходили и не имеют партий;
  деплой на VPS (ждёт ответа про домен).

### Онлайн-игра (2026-10-15, этап 2)

- **Как играть.** «Онлайн» → время (1+0 … 30+0), цвет → «Создать партию» → ссылка `#online/<id>` уходит другу →
  он открывает, жмёт «Играть как гость» (или входит через Google, после чего возвращается на ту же ссылку) →
  партия начинается. Кто угодно с ссылкой может смотреть. После конца: карточка итогов, «Смотреть отчёт»
  (PGN уходит в разбор), «Реванш» (обоюдное согласие, цвета меняются). Партии лежат в профиле, вкладка «Партии».
- **Сервер** (`backend/internal/play`, пакет подключён только при наличии базы). Сервер единственный источник
  правды: ход проверяется правилами фасада движка (`LegalMoves`, `Outcome`), мат, пат, повторение, 50 ходов и
  недостаток материала определяются движком. Часы на сервере: время хода считается по часам сервера, а не
  клиента; добавка за ход; пока оба не сделали по ходу, часы стоят, а на первый ход даётся 60 с (иначе партия
  отменяется без результата, как на lichess). Флажок: таймер на момент окончания времени игрока, а ход,
  пришедший после, отклоняется; если у соперника только король (или король и один конь/слон), падение флажка
  даёт ничью. Сдача, предложение и принятие ничьей, отмена в начале партии, реванш.
- **WebSocket** (`github.com/coder/websocket`, единственная новая зависимость): `GET /api/games/{id}/ws`. Клиент
  шлёт `move`, `resign`, `draw`, `drawDecline`, `abort`, `rematch`; сервер после каждого изменения шлёт всем
  **целый снимок** партии (ходы, часы, предложения, присутствие, кто вы, допустимые ходы только тому, чей ход).
  Целые снимки вместо дельт: переподключившийся клиент просто получает состояние и не может разойтись с
  сервером. Клиент сам переподключается (0,5 → 5 с), вкладка, вернувшаяся из сна, сразу. Ограничения: 4 КиБ
  на сообщение, не больше ~5 сообщений в секунду, медленный клиент отключается (не тормозит партию), проверка
  `Origin` против перехвата сокета чужим сайтом, пинг каждые 25 с.
- **Другие запросы:** `POST /api/games` (цвет, время; нужен вход, до 5 неотвеченных приглашений на человека),
  `POST /api/games/{id}/join`, `GET /api/games/{id}` (то же, что присылает сокет), `GET /api/games/{id}/pgn`
  (после конца), `GET /api/games` (мои партии). Приглашение живёт сутки.
- **Хранение.** Партия целиком (ходы, часы, предложения) лежит в памяти и после каждого изменения пишется в
  MySQL (`games`, миграция 0004, JSON `state` и столбцы для списков); при перезапуске сервера партия
  поднимается из базы при первом обращении, часы продолжают идти, клиенты переподключаются сами (проверено
  `docker compose restart server` посреди партии). Из памяти партии уходят через 10 минут после конца, если
  на них никто не смотрит. Слияние аккаунтов (гость → существующий Google) переносит и онлайн-партии.
- **Nginx:** отдельный `location` для сокета (`Upgrade`, `Connection`, таймаут 1 ч), `Host $http_host` (проверка
  `Origin` сравнивает с хостом вместе с портом); Vite проксирует `/api` с `ws: true`. Вход через Google
  принимает `?next=#online/<id>` (только хеш-маршрут сайта, не URL) и возвращает на ту же страницу.
- **Тесты:** `internal/play` (`-race`): правила и очерёдность, мат, повторение, часы и добавка, падение флажка
  (в том числе ход после падения, ничья против голого короля), отмена за отсутствие первого хода, ничья,
  сдача, отмена, реванш, права зрителя, присутствие, медленный клиент, сохранение и восстановление (включая
  подделанный ход), PGN читается разборщиком; сокеты поверх `httptest` с живым WebSocket-клиентом (партия
  вдвоём до мата, зритель, ошибка и правдивый снимок после плохого хода, ничья/реванш, чужой `Origin`,
  перезапуск). `internal/store` на настоящей MySQL. `npm test`: время, формат часов, итоги. В Edge с тремя
  браузерами (создатель, соперник, зритель): приглашение, вход гостем, ходы кликами, часы, перезагрузка
  страницы, ничья с отказом и согласием, реванш, сдача, разбор из профиля, перезапуск сервера, мобильная ширина.
  Отдельно: настоящие часы на сервере (партия 10 с, флажок упал через 9,8 с).
- **Не сделано:** рейтинг и подбор по очереди; предходы;
  чат; удаление просроченных приглашений из базы; отдельное правило для ушедшего игрока (часы
  просто идут, и он проигрывает по времени); звук/уведомление о предложении ничьей.

- **Раскладка как на странице «Игра против движка»** везде, где есть доска: онлайн-партия и партия с ботом (`online.css`), разбор (и страница, и на месте; `review.css`, класс `page--stage`), выбор бота (`bots.css`). - **Игра с ботом это обычная онлайн-партия** (`play`): бот занимает второе место, ходит сервер (с короткой «человеческой» паузой), поэтому работают часы, сдача, отмена в начале, реванш (бот всегда соглашается, цвета меняются), разбор на месте, запись в профиле и переподключение. Предложение ничьей бот принимает, если он явно хуже (оценка минус 120 сотых пешки и хуже), иначе отклоняет. Партия переживает перезапуск сервера: бот, которому надлежит ходить, ходит сразу после открытия партии. Поиск бота ограничен семафором (половина ядер), у человека не больше 8 незаконченных партий с ботами.
- **Очки и «побеждён».** За первую победу над ботом начисляются очки (10 у Миши, 150 у Максимума; растут с силой бота), бот отмечается побеждённым; повторные победы очков не приносят; ничьи и поражения тоже считаются. Всё считает сервер по концу партии (мат, время, сдача), таблица `bot_progress` (миграция 0005). Страница ботов показывает «очков · побеждено N из 10» и «побеждён» у каждого, карточка итогов после первой победы говорит «Бот побеждён! +N очков», профиль (вкладка «Обзор») показывает очки и побеждённых. При слиянии аккаунтов (гость → Google) прогресс объединяется, очки считаются один раз.
- **Тесты:** `internal/bots` (реестр, каждый бот ходит легально, сильные видят мат в один ход, самый слабый зевает ферзя чаще сильного, вынужденный ход мгновенен), `internal/play` (партия с ботом от хода до сдачи, бот ходит первым, отказ от ничьей и реванш, запись результатов ровно один раз, список ботов и прогресс, проверка запросов, и **человек**, которого играет сам движок через настоящий WebSocket, обыгрывает слабого бота: очки начисляются один раз), `internal/store` на MySQL (прогресс, слияние). В Edge: страница, выбор, партия с часами, ответ бота, предложение ничьей, сдача, реванш, профиль, мобильная ширина.

### Значки ходов, разбор на месте, новое меню (2026-10-15)

- **Десять значков** (девять плюс «упущенная возможность») от «зевка» до «блестящего»: ?? зевок, ? ошибка, ?! неточность, теория, ✓ хороший, «палец вверх» отличный, звезда лучший, ! сильный, !! блестящий. Новые два класса (`backend/internal/analysis/special.go`, все пороги там константами):
  - **Блестящий**: ход почти ничего не потерял (лучший или отличный), при этом по линии движка игрок отдаёт материал (после размена остаётся минус 2 пешки и больше), позиция не была выиграна заранее (до 85%) и осталась не хуже примерно равной (от 40%). Исключение: жертва ради форсированного мата засчитывается и при большом преимуществе. Превращение жертвой не считается.
  - **Сильный**: «единственный ход». Играет лучший ход движка, а каждый другой ход заметно хуже: лучшая альтернатива отстаёт не меньше чем на 15 пунктов вероятности победы. Многолинейного поиска у движка нет, поэтому альтернативы проверяются прямо: каждый ход разыгрывается и позиция ищется на 5–9 слоёв. Не считается в уже решённой позиции (меньше 8% или больше 85%), если игрок отвечает на шах или отбирает фигуру, если соперник только что сделал ошибку (забрать зевок не находка), в дебютной теории и при единственном ходе.
  - **Упущенная возможность** (`miss`): неточность или ошибка, сыгранная сразу после ошибки соперника (он потерял от 10 пунктов вероятности), когда ходящий стоял явно лучше (от 60%): упущено то, что подарил соперник. Зевок остаётся зевком. Пороги `MissMinPrevLoss`, `MissMinBefore` в `special.go`.
  - Эвристики проекта, не копия правил какого-либо сайта; пороги подбираются по реальным партиям. На «Опере Морфи» блестящим отмечен 16.Qb8+, в «Бессмертной партии» 22.Qf6+; на обычной партии лишних значков нет. Цена: до ~30 дополнительных коротких поисков на каждый лучший ход (разбор партии в 100 позиций на глубине 12 по-прежнему занимает около 2 секунд). Отключается `Options.NoSpecial`. Тесты: чистые функции (материал, линия, жертва, пороги), разбор «Оперы» с проверкой блестящего хода и NoSpecial.
- **Интерфейс разбора.** Значок хода рисуется на доске в правом верхнем углу поля, куда пошла фигура (контекст в `ThemedBoard`, поле само не перестраивается). Карточка «текущий ход» поднята в правую колонку на самый верх: большой значок, ход, название типа, пояснение одной фразой (место для будущего ИИ-тренера) и оценка с линией движка.
- **Разбор без смены страницы.** «Смотреть отчёт» после партии (с ботом и онлайн) не уходит на другую страницу: поверх экрана партии открывается разбор (`review/ReviewInline`), доска остаётся той же позиции, справа панель прогресса «Анализирую партию…» превращается в разбор, который открывается на последнем ходе партии; «К партии» возвращает назад. Адрес в строке браузера не меняется. Разбор сохраняется у вошедшего пользователя как обычно. Опрос задания вынесен в хук `useAnalysis`, им же пользуется страница «Разбор партии».
- **Меню** (по частоте использования): «Играть» с выпадающим списком (Играть онлайн, Играть с ботами (скоро), Играть против движка), Задачи, Дебюты, Уроки (скоро), Разбор партии, Тренер (скоро); внизу «Настройки» и карточка профиля слева снизу (вошедшему ведёт в профиль, остальным предлагает войти). На узком экране список «Играть» всплывает над нижней панелью. Страница бота названа «Игра против движка». «Игра с ботами» (боты разной силы) ещё не сделана.

### Задачи (2026-10-15)

Загружено 80 816 задач (`puzzleimport` по файлу в 307 МБ из 6,2 млн строк: 3,1 млн отброшено как неустоявшиеся или малоиграные, ни одной с неверной цепочкой). Страница пройдена в браузере (Edge, puppeteer-core): решение задачи даёт +18, показ решения считается неудачей (−26), подсказка отмечает фигуру, точки ходов и кольца взятия на месте.

- **База.** Миграция `0006_puzzles.sql`: `puzzles` (id, FEN, ходы, рейтинг, популярность, темы), `puzzle_themes` (по строке на тему, с рейтингом для выборки диапазоном), `puzzle_ratings` (рейтинг, число попыток и решённых у человека), `puzzle_attempts` (первая попытка по каждой задаче). Идентификаторы задач регистрозависимы (`ascii_bin`). Слияние гостя с аккаунтом Google (`MergeUsers`) переносит попытки и складывает рейтинги (остаётся рейтинг того аккаунта, где попыток больше).
- **Импорт.** `go run ./backend/cmd/puzzleimport -file <lichess_db_puzzle.csv.zst> -dsn ...`: читает CSV (в том числе `.zst`, пакет `klauspost/compress`), оставляет самые популярные задачи каждой сотни рейтинга (около 100 000 всего, фильтры: отклонение рейтинга до 90, популярность от 85, сыграно от 200 раз), проверяет, что цепочка ходов допустима, и добавляет в MySQL пачками. Повторный запуск добавляет только новые.
- **API** (`backend/internal/puzzles`): `GET /api/puzzles/next?theme=` (задача около рейтинга человека, окно ±100 расширяется до всего диапазона; непробованные раньше), `GET /api/puzzles/{id}`, `GET /api/puzzles/themes`, `POST /api/puzzles/{id}/result` (`{solved}`). Браузер не знает правил, поэтому сервер прикладывает к каждому шагу позицию после хода, а к ходам человека ещё список допустимых ходов и другие мат-ходы (любой мат засчитывается, как на Lichess). Цепочка строится через фасад движка.
- **Рейтинг.** Эло против неизменного рейтинга задачи; старт 1000; K = 48 первые 10 попыток, 32 до 50-й, затем 20; пол 100. Считается только первая попытка по задаче: неверный ход или показ решения — неудача, дальнейшее решение тренировочное. Результат присылает браузер и доверяется (рейтинг личный).
- **Страница** `web/src/puzzles/`: раскладка комнаты (`.room`), общий компонент `Board` (получил свойства `hint` и `badge`: значки «лучший ход» и «зевок» из `review/badges` на клетке хода), подсказка подсвечивает фигуру, русские названия тем в `themes.js`, чистая логика проверки хода в `puzzle.js` (тесты `puzzle.test.js`). Гость создаётся автоматически при открытии, как на странице ботов.
- **Ограничения.** Нет задачи дня, Puzzle Rush, задач из своих ошибок, истории попыток.

### Доска: точки возможных ходов (2026-10-15)

Возможные ходы выбранной фигуры показываются тёмными полупрозрачными точками (кольцо вокруг фигуры, которую можно взять, и поля взятия на проходе), как у chess.com, а не квадратной рамкой. Точки рисует `OverlaySquare` в `components/ThemedBoard.jsx` поверх клетки (под фигурой, мыши не мешают), стили `.sq-dot` и `.sq-ring` в `review/review.css`, выбор точка или кольцо в `components/Board.jsx` (по FEN). Точки появляются и при перетаскивании фигуры. Это общий компонент `Board`: так выглядят игра против движка, онлайн-партии, партии с ботами и задачи. Проверено только сборкой (`vite build`), в браузере глазами не смотрелось.

### Разбор: своя ветка, копирование, материал, режим доски (2026-10-15)

- **Копирование.** В карточке партии справа от доски: «Копировать FEN» (позиция, которая сейчас на доске, в том числе внутри своей ветки) и «Копировать PGN» (вся партия с заголовками: игроки, результат, дата, стартовая позиция); в карточке ветки кнопка «Ветка» копирует ходы ветки. Буфер обмена: `review/clipboard.js` (современный API, запасной путь через textarea).
- **Своя ветка.** Доска разбора теперь живая (общий компонент `Board`): можно взять фигуру и сходить из любой позиции партии. Если ход совпал со следующим ходом партии, это просто шаг вперёд; иначе открывается ветка: ходы идут в карточку «Своя ветка», по ним можно ходить назад и вперёд, нажимать на любой ход, а «К партии» или Esc возвращает на тот же ход партии. Каждую позицию ветки оценивает движок, а у хода появляется значок и потеря в процентах («Ошибка (−14%), лучше было Nf3»; пороги те же, что у разбора, `review/branch.js`). Ходы «лучшей линии» движка в карточке хода нажимаются: нажатие разыгрывает линию до этого хода на доске. Кнопка «Сыграть ход движка».
- **Сервер.** Браузер правил не знает, поэтому новый `POST /api/line` (`backend/internal/api/line.go`): `{fen, moves[] (UCI или SAN), eval, depth}` → шаги с позициями, допустимые ходы последней позиции, статус (мат или ничья) и по запросу оценка (`analysis.AnalyzePosition`, глубина как у разбора, не больше `MaxDepth`). Одновременно считаются только две оценки (`lineEvalSlots`), чтобы толпа не вытеснила очередь разборов.
- **Материал.** Рядом с именем игрока показаны взятые им фигуры и «+N», если он впереди (`components/Captured.jsx`, подсчёт в `components/material.js`: превращённая пешка не считается взятой). Есть в разборе, онлайн-партиях и партиях с ботами, против движка (там добавлены полосы с именами над и под доской), задачах. Фигуры рисуются текстовыми символами шахматных фигур: для пользовательских наборов фигур картинки не используются.
- **Режим «Доска в центре».** Пункт в левом меню (виден на страницах с доской: разбор, игра против движка, задачи, партия онлайн или с ботом) убирает меню и все панели, доска растёт и стоит по центру; выход: Esc или плавающая кнопка справа сверху. Стили `.shell--focus` в `Root.css`. Остальные сведения остаются на панелях, поэтому в этом режиме не видны ходы, сдача, чат.
- **Значки.** В `review/badges/` лежат все десять картинок (PNG 256×256 с прозрачностью); код подхватывает их сам. Проверено в браузере (puppeteer-core и Edge): адреса вида `/assets/best-DGEDUUA7.png` это и есть файлы из этой папки, Vite кладёт их в `dist/assets/` с хешем в имени, хеши содержимого совпали с файлами папки. Если на сайте видны старые значки или нет новых кнопок, значит работает старая сборка: нужна пересборка (`docker compose up -d --build`, сервер тоже, потому что появился `/api/line`). Чтобы браузер не держал старый `index.html`, nginx теперь отдаёт его с `Cache-Control: no-cache`. Размеры картинок значков (были 22 и 32 пикселя, на экране мелко и мыльно): в списке ходов 30, в карточке хода 48, на поле доски около 0.44 клетки; у нарисованных значков без картинки размеры прежние (`review/ClassBadge.jsx`).
- **Материал.** Если выбран набор фигур с картинками, взятые фигуры рисуются ими; для стандартного набора используются текстовые символы. В задачах показывается только перевес («+N»).
- **Тест.** `TestBeatingABotEarnsPointsOnce` стал падать из-за предела частоты сообщений по WebSocket (20 в запасе и 5 в секунду): «игрок» там сам бот и играет быстрее человека. Предел вынесен в переменные `msgBurst` и `msgRate` (`play/hub.go`), тест их поднимает.

### Дебюты: репертуар и заучивание (2026-10-15, этап 4, первая часть)

Образец: Chessbook (по обзорам: репертуар строит сам человек, ходы повторяются с интервалами, ошибки возвращаются скоро, разбор партий на отклонения). Решения автора: без внешней статистики популярности ходов, нескольких репертуаров на человека, порция новых ходов 10 за раз.

- **Данные** (миграция `0007_repertoires.sql`): `repertoires` (имя, цвет) и `rep_moves` (дерево ходов: родитель, UCI, SAN, FEN после хода, номер полухода, признак «мой ход»). Состояние повторения хранится в строке самого хода (ступень лестницы, когда спросить, ошибки, число ответов), потому что ходы человека и есть карточки. Пределы: 30 репертуаров на человека, 5000 ходов в репертуаре (`store.ErrLimit`). Слияние гостя с аккаунтом Google переносит репертуары.
- **Лестница** (`backend/internal/repertoire/ladder.go`): после верного ответа ступень растёт, ход спрашивают через 10 минут (ступень 0), 1, 3, 7, 14, 30, 90 дней; выучен с ступени 5. Ошибка: падение на две ступени, повтор через 10 минут. Время подставляется через `Config.Now`, поэтому логика проверяется тестами.
- **Тренировка** (`train.go`): `Select` берёт просроченные карточки (самые давние первыми, до 40), потом новые в порядке добавления в репертуар, то есть линия за линией от начала (до `new`, по умолчанию 10, не больше 50). `BuildDrill` строит вопрос: путь от начала до позиции, ответ, другие ходы репертуара в той же позиции (они не ошибка, но не тот, что спрашивают) и допустимые ходы, потому что браузер правил не знает. `Gaps` находит линии, заканчивающиеся ходом соперника.
- **API:** `GET/POST /api/repertoires`, `GET/PATCH/DELETE /api/repertoires/{id}`, `POST /api/repertoires/{id}/moves` (сервер проверяет ход и сам определяет, чей он по цвету репертуара и номеру полухода), `DELETE .../moves/{move}` (с продолжениями), `GET .../train?new=`, `POST .../review` (`{move, correct}`). Все требуют входа (гость подходит); чужой репертуар отдаёт 404.
- **Сайт** (`web/src/openings/`): список (`OpeningsPage.jsx`), конструктор (`Builder.jsx`), тренажёр (`Trainer.jsx`), чистая логика с тестами: `tree.js` (дерево, статусы ходов, счётчики) и `session.js` (очередь вопросов: новый ход показывается и возвращается вопросом, ошибка возвращает ход через три вопроса, серверу уходит только первый результат хода за сессию). Раскладка комнаты (`.room`), доска общая; режим «Доска в центре» работает и здесь. Адреса: `#openings`, `#openings/<id>`, `#openings/<id>/train`.
- **Подсказки конструктора** (2026-10-15, по просьбе автора: «чтобы сайт сам предлагал продолжения, пользователь выбирал, сайт показывал оценку после хода, потом тренировать или менять»): `POST /api/continuations` (`backend/internal/api/continuations.go`, `TheoryMoves`) отдаёт ходы из позиции, ведущие по линиям справочника ECO, с названием дебюта и числом линий справочника, проходящих через позицию после хода (`eco.Book.Lines`, считается при загрузке книги). Это замена популярности из базы партий: у e4 около 2000 линий, у d4 около 1300, у c4 около 200, у a3 пять. Оценку каждого хода сайт спрашивает у `POST /api/line` (`eval`, глубина 10; позиции 12), по два запроса одновременно (`makeQueue` в `openings/suggest.js`), поэтому список появляется сразу, а оценки подтягиваются. `buildSuggestions` складывает три источника в строки: ходы репертуара, теория (по числу линий, слабые с потерей от 10% в конце), лучший ход движка; потеря считается как в разборе (`moverLoss`). Нажатие на строку играет ход (добавляет или идёт дальше по уже добавленному); после добавления баннер «Тренировать / Отменить добавление / Продолжить линию». Компонент `openings/Suggestions.jsx`.
- **Статистика Lichess и разбор отклонений в партиях** (2026-10-15, по просьбе автора: «разбор отклонений в твоих партиях и настоящая статистика из Lichess»):
  - *Статистика.* Пакет `backend/internal/explorer`: прокси к `https://explorer.lichess.ovh/lichess` (`GET /api/explorer?fen=&ratings=&speeds=`). Explorer **требует токен** (без него 401, проверено): `LICHESS_TOKEN` из окружения (в `docker-compose.yml` и `.env.example`), токен не покидает сервер. Отвечает только вошедшим (гость подходит), параметры чистятся по белым спискам, ответы запоминаются на 24 часа (до 5000), просьбу Lichess подождать (429, `Retry-After`) сервер соблюдает: пока пауза, запросы наружу не идут. Без токена `{available:false}`. Ход рокировки Lichess пишет как «король берёт свою ладью» (`e1h1`), сервер переводит в ход короля (`e1g1`). Ответ нормализован: всего, белые, ничьи, чёрные, ходы с числом партий, результатами и средним рейтингом. На сайте `Suggestions.jsx`: процент и число партий, полоса результатов, выбор рейтинга (запоминается), порядок по числу партий, редкий ход (меньше 1% партий), честное сообщение, если токена нет или Lichess просит подождать. Справочник ECO остаётся для названий дебютов и запасным источником.
  - *Разбор партий.* `repertoire.Compare` (чистая функция с тестами) ведёт ходы партии по дереву и находит первый выход из него: `you-deviated` (в вашу очередь в репозитории был ход, а сыграли другой), `opponent-deviated` (соперник сыграл не то, что вы ждали), `book-ended` (в репозитории здесь вообще нет ходов), `in-book`, `empty`, `broken`. `GET /api/repertoires/{id}/games` берёт последние 80 партий человека (таблица `games`: онлайн и с ботами), оставляет партии его цвета (не короче двух ходов), сравнивает до 30. Страница `GamesReview.jsx` (`#openings/<id>/games`): забытый ход можно вернуть в тренировку (`POST .../review` с ошибкой), а ход соперника или конец линии добавить: `#openings/<id>/move/<узел>/<ход>` открывает конструктор на нужной позиции, предварительно добавив этот ход. **Вставленные партии (2026-10-16):** `POST /api/repertoires/{id}/compare` (`repertoire/pasted.go`, `comparePasted` с тестом `TestComparePasted`): PGN из тела разбирается `pgn.ParseString` (главная линия), каждая партия считается сыгранной человеком за цвет репозитория; необязательное поле `name` оставляет только партии, где за этот цвет играл человек с таким именем в тегах White/Black (без учёта регистра). Пропускаются партии со своей начальной позицией, чужого цвета и короче двух ходов; если одна партия файла сломана, сравниваются партии до неё и приходит `warning`. Ответ как у `/games` плюс `read`, `skipped`, `warning`; в `GameJSON` добавлено поле `date` (тег Date). На странице `GamesReview.jsx` форма «Проверить свои партии из PGN» (файл или текст, имя запоминается в `localStorage`), результат заменяет список партий с сайта, есть кнопка возврата. Проверено в Edge: три партии, имя «Dyanis» оставило две, победа по репозиторию и выход соперника (1...e6), кнопки «Добавить этот ответ» и «Открыть позицию».
  - *Проверено в браузере* (Edge, puppeteer-core): три партии против бота вставлены в базу в формате сервера, разобраны верно (забытый Nf3, уход соперника 1...c5, конец линии), действия работают; статистика проверена на подставном ответе (проценты, полосы, смена рейтинга даёт новый запрос), на ответе «подождите» и без токена. **С настоящим токеном Lichess не проверялось**: токена нет, его создаёт автор.
- **Название для человека** (решение автора, 2026-10-15): на сайте это «**репозиторий ходов**», а не «репертуар» (так понятнее). В коде и в этом плане остаётся `repertoire` и «репертуар». Строки сайта и сообщения сервера уже переименованы.
- **Оценка отклонений в тренажёре:** если человек сыграл не тот ход, `Trainer.jsx` просит у `/api/line` оценку позиции после его хода и после нужного хода (глубина 10) и сравнивает их `deviationVerdict` (`openings/session.js`): потеря до 5% — «ход хороший, но мы учим другую ветку», от 5% — «неточный, теряет около N% шансов, мы учим другой ход», от 15% — «грубая ошибка, так играть не надо». Для хода, который есть в репозитории, но не тот, что спрашивают, текст «этот ход тоже есть в репозитории, но мы учим другую ветку» (не ошибка). Любой неверный ход, подсказка или «показать ход» остаются неудачей для лестницы повторений. Значок на поле: хороший, неточность или зевок.
- **Прокрутка:** страница конструктора прыгала вниз к дереву линий при каждом ходе, потому что активная строка дерева вызывала `scrollIntoView` (он двигает и страницу). Заменено на `scrollWithin` (`ui/scroll.js`): двигается только собственная прокрутка списка. Так же исправлен список ходов на странице разбора. Проверено: за 8 ходов страница не сдвинулась ни на пиксель.
- **Проверено в браузере** (Edge, puppeteer-core): создание репертуара, пять ходов основной линии и ветка ходами на доске, «дыра» и её исчезновение после удаления хода, тренировка из четырёх новых ходов (показ, повтор, вопрос), ошибочный ход (ход упал на ступень 0, 1 ошибка, вернётся через 10 минут), «На сегодня всё» после сессии.
- Что осталось от дебютов: см. «Что не сделано / дальше» выше.

## 7. Сознательно не делаем

Клубы, форум, новости, личные сообщения, подписки и платежи, турниры, трансляции, мобильное приложение, многоязычность, антиплагиат (кроме простых лимитов).

## 8. Риски

1. **Часы и рассинхронизация** — время считает сервер, клиент только показывает; учесть
   задержку, проверять на тестах с искусственной потерей пакетов.
2. **Нагрузка анализа** — один анализ занимает секунды CPU. Нужны очередь, лимит параллельных
   задач, отмена, кэш. Иначе одна партия вешает сервер.
3. **Шкала оценок NNUE** отличается от привычной — подобрать K для вероятности выигрыша
   (раздел 4.1), иначе пороги ошибок будут «кривыми».
4. **Состояние партий в памяти** — при перезапуске сервера активные партии теряются;
   решить сохранением ходов в БД на каждый ход и восстановлением.
5. **Лицензии**: книги дебютов, база задач (Lichess — CC0), шрифты и звуки; не копировать тексты, дизайн и бренд chess.com.
6. **Очередь подбора и дуэли живут в памяти**: после перезапуска сервера ожидающие и идущие дуэли теряются (партии с часами сохраняются в базе).
7. **Docker и движок**: в образ сервера нужно положить сеть `net-kingf-m4.bin` и книги, а
   Go собирать с тем же набором флагов, что и локально (`GOEXPERIMENT=simd` работает только
   на amd64 и требует AVX2 на хосте; на VPS это проверить командой `lscpu`). Проверка
   сборки в контейнере — тест «те же узлы и оценки на фиксированной глубине, что и локально».
8. **Google OAuth**: для публичного домена нужен экран согласия в статусе «тестирование»
   (до 100 тест-пользователей) или проверка приложения Google; для защиты хватит
   «тестирования», но тестовых пользователей надо добавить заранее. Redirect URI должен
   совпадать с доменом точно (`https`, без опечаток), иначе вход падает с ошибкой.
9. **Миграции MySQL**: схема меняется каждый этап, поэтому миграции с самого начала, а не
   `CREATE TABLE` руками. Кодировка `utf8mb4`.

## 9. Что нужно решить

1. **Где запускать**: локально или на сервере с доменом (VPS). Для публичного адреса нужны домен, HTTPS и redirect URI Google.
2. **ИИ-тренер**: допустим ли внешний LLM (ключ и расходы) или только своими силами.

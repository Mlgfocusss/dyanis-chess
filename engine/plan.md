## Как здесь принято работать (важно соблюдать)

- **Маленькие, независимо проверяемые шаги.** Не наслаивать несколько
  независимых изменений в один заход.
- **Силу игры меряет только матч (`cmd/match`)**, не число узлов и не
  тактический suite. Узлы (`cmd/profile`) отвечают только за скорость;
  тактический suite (`go test -v -run TestTacticalSuite ./internal/search`)
  — проверка, что ничего не сломано, а не термометр силы.
- **Порядок работы над изменением поиска/эвала:**
  1. `go build -o baseline.exe ./cmd/cli` ДО правки (или взять
     существующий `baseline.exe`, если он соответствует текущему коду);
  2. правка; `go vet ./internal/search`;
  3. `go build -o candidate.exe ./cmd/cli`;
  4. `.\match.exe -a candidate.exe -b baseline.exe -movetime=100
     -pairs=300 -concurrency=16 -elo0=0 -elo1=10 -openbook=assets/gm2001.bin`
     (≈ 7 минут на 100 мс; для 500 мс `-concurrency=8`; запускать
     в фоне, ноутбук не выключать);
  5. если SPRT не закрылся — вторая серия с `-seed=2` в тот же
     `"-carry=файл"` (кавычки обязательны в PowerShell 5.1 — иначе
     `-seed` молча теряется), итог считается по всем парам сразу;
     принимать, если нижняя граница 95%-интервала выше нуля. Интервал
     теперь по парам (пентаномиальный) — уже, чем у старых серий в этом
     файле, поэтому старые цифры «±15» и новые между собой напрямую не
     сравнивать;
  6. принято → `go test ./internal/search`, `baseline.exe` пересобрать
     из нового кода, описать в `TECHNICAL.md`; не принято → откат
     полностью, без остатка, запись сюда в «Реализовано, откачено».
- **Гипотеза может не подтвердиться — это нормальный исход, не провал.**
  Мёртвый код и неиспользуемые поля хуже чистого отката.
- **`go run` на Windows не всегда пересобирает надёжно** — для сравнения
  до/после всегда `go build -o что-то.exe`, потом запуск exe.
- **`go test -race` на Windows** требует cgo и настоящего C-компилятора
  (ставили `winget install BrechtSanders.WinLibs.POSIX.UCRT`, `bin` в
  `PATH`, `go env -w CGO_ENABLED=1`).
- **Фоновые команды с параметром `timeout` убиваются по его истечении** —
  для матчей (>10 минут) `timeout` не задавать.
- Тестов на `internal/eval` **сознательно нет** (кроме интеграционных
  `Evaluate()`) — решение автора проекта.
- Эвал автор уже много раз тюнил Texel'ом — новые термы эвала не
  предлагать без явной просьбы.

### Пакет 1 — сделан 2026-10-23, ждёт проверки на новых сидах и на 500 мс

### Пакет 2 — pruning и редукции — СДЕЛАН 2026-10-23 (пункты 5, 6, 7 и LMR−1 в PV из 8)
5. Null-move: сейчас R=2 фиксирован, условие `staticEval >= beta`, возвращается
   `beta` (negamax.go:15, 401–417). Современно: R≈3+depth/3+min((eval−beta)/200,3),
   fail-soft (вернуть nullScore, если не мат), при depth>=12 проверочный поиск.
   Новые tunables NmpBase/NmpDivDepth/NmpEvalDiv/NmpEvalMargin, потом SPSA.
   Прежние варианты (R=2+depth/6: +6±15; R+1 при eval−beta>200: +5,2±21) оба
   положительные и слабые, полной формулы с R 5–7 на глубине 10+ не было.
   +5…+12.
6. Futility, LMP и SEE-pruning заканчиваются на глубине 3
   (`futilityMaxDepth`, `lmpMaxDepth`, negamax.go:90, 122; SEE-pruning только
   взятий до depth 6). SPSA крутила пороги, а не диапазоны. Сделать до depth 6–8:
   futility по lmrDepth, LMP порог ~(3+depth²)/2, SEE-pruning тихих ходов
   `SEE < −c·lmrDepth²`, history-pruning на depth ≤ 4–5 (после continuation
   history). +8…+15 суммарно.
7. IIR вместо IID: без TT-хода и при depth>=4 просто `depth--` вместо лишнего
   `negamax(depth−2)` (negamax.go:515–523). Заодно убрать второй `tt.probe(hash)`
   на строке 491. +3…+8.
8. LMR (negamax.go:647–689, `lmrFullDepthMoves=4`): нет поправок на PV, cutNode,
   TT-взятие, историю; редукция начинается только с 4-го хода. Сделать
   `LmrFullMoves` отдельно для PV и не-PV (2–3), r−1 в PV, r+1 в cutNode (нужен
   параметр `cutNode`), r+1 если TT-ход — взятие, r−1 при хорошей history.
   +5…+12.

10. Correction history под NNUE: поправка статического эвала по pawn- и

### Мелкие дефекты и скорость
12. Qsearch (quiescence.go): fail-hard (возвращает `beta` на 174, 248 и пишет в

    сортируются (120) и `GenerateLegalMoves` аллоцирует на куче (109). Нет тихих
    превращений в ферзя (`generatePseudoLegalCaptures`, movegen.go:364–412). В

13. Чистые ускорения, проверяются одинаковыми нодами на фиксированной глубине,
    вместе ≈5–10% nps:
    - `hasNonPawnMaterial` (negamax.go:178–189) идёт циклом по 64 клеткам и
      вызывается раньше дешёвого `getStaticEval() >= beta`: заменить битбордами
      и переставить условия;

### Время, эндшпиль, потоки (в матчах movetime почти не видно)
15. Управление временем (uci.go:455–474): плоская доля `time/30 + 3/4·inc`. Нужны
    мягкий и жёсткий лимит, новая итерация не начинается после ~50–60% бюджета,
    продление при нестабильном лучшем ходе. `go infinite` и `ponder` молча
    игнорируются. +10…+25 на реальных часах, мерить партиями с `wtime/btime`.
16. Lazy SMP (search.go:465–482): потоки идут по одним глубинам одним порядком.
    Нужен пропуск глубин по номеру потока, разные стартовые глубины, голосование
    по ходам. Влияет только при threads>1 (сайт, анализ), +10…+30 при 4+ потоках.
17. Эндшпиль: `mopupScore` (eval/mopup.go) с NNUE не используется. KRK находится
    как мат только на глубине 18 (~1,5 с), KBNK и KBBK до глубины 16–18 стоят на
    ~800 cp без градиента. Добавлять mop-up к оценке сети при голом короле
    противника и перевесе. Нет масштабирования эвала от `HalfmoveClock` (например
    `eval·(200−rule50)/200`) и контемпта. Syzygy вычеркнут автором 2026-10-09.
